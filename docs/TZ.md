# ТЗ: сайт AutomatonSoft v2

Статус: черновик на утверждение. Дата: 2026-11-17.

## 1. Зачем сайт

Сайт продаёт разработку AI/ПО под задачу клиента. Две работы:

1. **Показать проекты** как доказательство, что мы умеем.
2. **Лендинги по отраслям и профессиям**: боль клиента, как мы её решаем, кейс, заявка.

Успех = входящие заявки от целевых клиентов. Всё, что не помогает заявке или доверию, в первую версию не входит.

## 2. Аудитория

- Основная: владельцы и руководители малого и среднего бизнеса в DACH (DE/AT/CH), которым нужна автоматизация рутины.
- Вторая волна: другие страны ЕС, английский язык.
- Не целимся пока: B2C-продукты, Enterprise, промышленные лицензии. Это идеи из исследования («100 вопросов»), а не задача сайта v2.

## 3. Объём версии 1

### Входит
- Главная.
- **5 отраслевых лендингов × 2 языка (DE, EN)** = 10 страниц.
- Портфолио: список + страница проекта (уже есть, переделываем под новый дизайн).
- Контакт + форма заявки.
- Компания (кратко), Impressum, Datenschutz.
- SEO: sitemap, hreflang, canonical, JSON-LD (Organization, FAQPage, BreadcrumbList).

### Не входит (отложено)
- Блог, B2C-страницы, страны × профессии (сотни страниц), AI-генерация страниц, личные кабинеты, платежи.
- Матрица «страна × профессия» делается только после того, как первые 5 лендингов приносят заявки.

### Первые 5 отраслей
Выбраны там, где у нас уже есть кейсы в портфолио (доказательство важнее красивых слов):

1. E-Commerce и маркетплейсы (товарные данные, Amazon/OTTO/Kaufland, возвраты)
2. Склад и логистика
3. Финансы и бухгалтерия (документы, счета)
4. Гостиничный бизнес
5. Промышленность (контроль качества, обслуживание)

Список можно заменить до начала Фазы 2. Не заменяем после.

## 4. Структура лендинга (шаблон)

Один шаблон, содержимое берётся из данных:

1. Hero: боль в одной фразе + CTA.
2. Цена проблемы: что клиент теряет (время, деньги, ошибки). Только проверяемые цифры.
3. Как решаем: 3–4 шага, без жаргона.
4. Кейс: 1–2 наших проекта из этой отрасли (скриншот, результат).
5. Интеграции: с чем работаем (ERP, CRM, маркетплейсы).
6. Как работаем и что стоит: модели сотрудничества (фикс / команда / поддержка).
7. FAQ: стоимость, защита данных (DSGVO), функции, интеграции, выгода.
8. Форма заявки.

## 5. Модель данных

Контент хранится данными, а не кодом. Новая отрасль = новая запись, без нового компонента.

> **Решение в фазе 2 (2026-11-17):** в версии 1 данные лендингов лежат в файлах `frontend/lib/landings/<отрасль>.js`, а не в Django. Причины: статическая сборка не зависит от боевого API, а 5 отраслей правят разработчики. Структура файла повторяет модель ниже, поэтому перенос в Django — отдельный шаг, когда контент начнут править не-разработчики. Отрасль заявки уже видна без новых полей: `attribution.landing_page`.

- **Industry**: slug, переводы (название, hero, боль, цена проблемы), порядок, опубликовано.
- **Pain / Step**: принадлежит Industry, переводы.
- **FAQ**: вопрос и ответ с переводами, группа темы (одна из 20, см. раздел 8а), тип (информационный / коммерческий), целевой поисковый запрос, связь с отраслью и/или услугой. Один вопрос может стоять на нескольких страницах.
- **Integration**: название, логотип, связь с Industry.
- **Project** (уже есть): связь многие-ко-многим с Industry.
- **ContactRequest** (уже есть): + поле «отрасль / лендинг, откуда пришла заявка».

Переводы: JSON-поле `translations`, как сейчас в `Project`. Поля из исследования (экономика, SEO-запросы, страны) добавляем позже, когда они понадобятся.

## 6. Дизайн

- Один дизайн-язык: типографика, сетка, палитра, 3–4 типа секций. Всё остальное собирается из них.
- Современный B2B-стиль: много воздуха, крупная типографика, чёткая иерархия, один акцентный цвет. Логотип и фирменный бирюзовый/navy сохраняем.
- Мобильная версия первичная.
- Анимации только лёгкие (CSS). Убираем курсор-фолловер и тяжёлые эффекты.
- Результат Фазы 1: варианты главной и лендинга как прототип; выбирается один.
- Контраст и доступность: WCAG AA.
- **Выбран тёмный дизайн B** (2026-11-18): navy-фон, бирюзовые акценты из логотипа, Space Grotesk для заголовков, Inter для текста.
- **Фирменная CTA-карточка** (`components/landing/cta-band.jsx`): бирюзовый градиент, полупрозрачное кольцо в углу, тёмная кнопка. **Крупных бирюзовых поверхностей на странице максимум две**: «сцена» под визуалом первого экрана и одна CTA-карточка. Плюс одна бирюзовая плашка-маркер в заголовке hero. В остальном градиент и кольцо повторяются только мелко (бейджи, подсветка).

## 7. Технические требования

### Стек (решение по умолчанию)
- Фронтенд: Next.js, статический экспорт, как сейчас.
- Бэкенд: Django оставляем как хранилище контента и приёма заявок.
- **Админка: штатная Django admin** вместо самописного дашборда на React. Меньше кода, редактирование контента из коробки.
- Один способ стилизации: Tailwind. Рукописный `public/assets/css/style.css` (879 строк) удаляем после переноса.
- Картинки через `next/image` (WebP/AVIF), шрифты через `next/font`.

### Производительность (проверяемые цели)
- Lighthouse mobile: Performance ≥ 90, Accessibility ≥ 95, SEO ≥ 95 на главной и на лендинге.
- LCP ≤ 2,5 с, CLS ≤ 0,1.
- JS на лендинге минимальный: только форма и меню.

### Структура репозитория
```
frontend/   Next.js
backend/    Django
deploy/     docker, nginx, скрипты деплоя
docs/       ТЗ, README
```
Сборка Docker и CI используют эти папки целиком, без ручных списков файлов.

### Сборка
- Данные для статики берутся из локального бэкенда в CI, а не с боевого сайта.
- Ошибка получения данных = падение сборки (сейчас молча подставляется пусто).

### Законодательство (Германия)
- Impressum и Datenschutz с реальными данными (сейчас есть плейсхолдеры, нужны данные от вас).
- Аналитика и мессенджеры только после согласия (cookie-баннер) либо без трекинга вообще.
- Форма заявки: согласие на обработку, ссылка на Datenschutz.

## 8. Контент

- Тексты лендингов пишем по шаблону из раздела 4. Черновик может делать AI, **но правит и принимает человек**.
- Никаких выдуманных цифр, клиентов и отзывов: в README уже есть правило, что без подтверждённых данных ставим «в подготовке». Сохраняем.
- Цифры экономии и стоимости (раздел 03 исследования: взносы в странах ЕС и т.п.) используем только с источником и годом.
- Google наказывает массовые одинаковые страницы. Каждый лендинг должен иметь уникальные боль, кейс и FAQ.

## 8а. FAQ и SEO-запросы (из ТЗ на 200 запросов)

Источник: «Техническое задание: 200 SEO-запросов в FAQ и Landing Pages». Берём правила, а не 200 страниц.

**Структура каждого ответа:** проблема клиента → вопрос → решение → этапы разработки → измеримый результат. Вопрос пишется языком клиента, ответ коротким (3–5 предложений).

**Группы тем (20):** программисты и разработчики; индивидуальная разработка; KI-Software; AI-агенты; автоматизация процессов; мобильные приложения; веб-приложения; сайты; E-Commerce; ERP; CRM; бухгалтерия и документы; логистика; промышленность; строительство и ремесло; чатботы и поддержка; API; SaaS; технологии и языки; MVP и модернизация. Это поле `topic` у FAQ, а не 20 отдельных страниц.

**Правила:**
- Информационные FAQ и коммерческие страницы услуг разделяем. FAQ ведёт на услугу и форму заявки.
- Ключевые слова вписываем естественно, без повторов. Дублирующих страниц не создаём.
- Экономию не обещаем. В каждом ответе про выгоду есть оговорка «зависит от процессов и степени автоматизации» (как в примерах ТЗ).
- Перед написанием проверяем объём, конкуренцию и намерение запроса. В источнике прямо сказано, что это не подтверждённый рейтинг.
- Язык ответов: язык страны (сначала DE, потом EN).

**В версии 1:** по каждой из 5 отраслей 6–8 FAQ (~35 штук) плюс 10–15 общих FAQ на странице услуг. Остальное из 200 запросов остаётся списком кандидатов и расширяется по данным Search Console.

**Важно:** сам список из 200 запросов в присланном PDF отсутствует, там только структура и 3 примера.
